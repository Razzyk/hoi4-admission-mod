# Stability guard provenance

The experimental stability guard in `native/stability/` is ported from the standalone project [Razzyk/hoi4-mp-stability-guard](https://github.com/Razzyk/hoi4-mp-stability-guard), source revision `a9c40d7ddf8f7320de0f7e69471c609003957984` (local reference checkout). The ported career-list and hook-transaction implementation is in `native/stability/career_guard.h` and `native/stability/stability_guard.c`; the pinned target constants are in `native/stability/target_spec.h`.

The target remains exactly HOI4 1.19.3.0, Windows x64, SHA256 `7dc947be34970da1e1c787bcddbe7f62b610ff258aebf8f06aa8b348f3a031d5`. The guard verifies that executable identity and the expected CALL bytes at RVA `0x1d6001` before patching. It serializes the complete career-profile daily work list when country tags repeat, preserving every entry and its statistics weighting; unique-tag lists continue through the original scheduler.

The standalone launcher's process creation, injection, profile handling, and launcher logging are not part of this port. Admission starts the guard from its worker thread after the lobby guard installs, routes diagnostic messages through the admission logger, and exposes stability state and statistics through admission exports. Guard verification is checked before service eligibility is granted and while the worker maintains its lease. The hook and its relay remain resident for the process lifetime.

This is an experimental workaround for the cooperative-country career-profile double-free race. It does not patch the separate army modifier teardown crash. The upstream validation describes synthetic regression and hook-installation checks; live campaign crash reduction, multiplayer synchronization, hot-join behavior, and performance have not been established.

For late automatic attachment, the patch transaction preallocates its thread inventory before suspending other threads, checks a fresh complete inventory while frozen, checks instruction pointers, and preserves prior suspension counts. It refuses incomplete or changed inventories before writing. Protection/cache-flush/thaw uncertainty poisons installation and withholds verification; the relay and wrappers remain mapped. There is no heap allocation, loader call or logging inside the frozen section. This assumes the normal single-manager attach flow; it is not a guarantee against another external injector creating threads or modifying code concurrently. Production builds omit diagnostic uninstall/exercise entry points.
